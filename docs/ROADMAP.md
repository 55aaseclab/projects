## 本次交付：完整 0.2.0 计划流程

当前任务实现完整计划合同，先 P0 后 P1 恢复；原生／浏览器／Core SDK 的实际功能证据已通过，部署及独立客户端／实体手机另行记录。本文不承诺发布日期、已分配的开发产能或生产可用性。

目标是形成共同计划：**一个项目主分支、四个团队主分支**（科研 `research`、工程 `engineering`、市场 `marketing`、支持 `support`），以及**按真实身份归属的个人分支**。每个范围都有 PRD 和 Roadmap。个人提案面向所属团队计划；团队贡献选择需要变更的项目内容，不整份替换项目 PRD，也不覆盖无关团队上下文。

## 决策、风险与发布边界

- **D1 已由 PRD 修订 3 确认，须实现受保护的角色及委托检查。** 平台维护／管理员身份、旧的自由文本负责人名称，都不赋予业务接受权。接受需要目标的指定决策角色及当前范围授权；外部智能体还需要针对该决策的显式委托。
- **A1 确定归属：** 默认每个 `(project, team, user)` 保留一个持续使用的个人分支，设计评审时确认。分支数量来自真实获授权参与情况，不编造成员。
- **A2 确定性能证据：** 测量前确认 PRD 提出的负载／延迟目标、指定环境及实际活跃并发量。不把未经测量的目标写成性能结果或服务保证。
- **D2 确定后续保留／删除规则：** 按现有项目策略保留已确认历史，不引入自动清理。**A3 确定建议范围：** 完整 P0 闭环先于 P1 恢复；排期和产能尚未确认。
- 独立修改不能静默覆盖对方。团队到项目的提案只提升有明确范围及来源的项目变更；同步保留团队自身语义。计划接受不能抹掉执行事实，也不代表已经预留现实资源。

实现检查使用隔离的合成记录。维护会话不填充或改写真实业务记录。依据 Praxis 验证方案，独立获授权业务客户端与实体手机证据分别记录；源码和浏览器夹具不能替代这些客户端。

后续运行版本先在所属仓库发布已验证的应用修订，再由 Praxis 固定可公开获取的版本并验证组合。按任务指定环境部署，并记录实际运行入口证据。本次运行版本须验证源码发布与部署；维护不操作真实业务记录。通过工作台需求阅读器打开中英文 PRD，在任务交付中记录实际文档检查结果；功能结果与其验证范围见 PRD 的当前 AC 台账。

## 既有独立运行与供数合同

维护空数据安装下的独立应用入口及 Praxis 集成。新增合同使用合成示例和测试。
